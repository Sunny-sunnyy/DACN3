108. Day 1 - Intro to MCP: The USB-C of Agentic AI  
Chào bạn, tôi là trợ lý giảng viên AI Engineering của bạn.
Chào mừng bạn đến với Tuần 6 (Week 6) - tuần lễ "chung kết" (Finale Week) của khóa học. Dựa trên hành trình dài mà bạn đã đi qua từ việc xây dựng Agent thủ công (Week 1), sử dụng OpenAI SDK (Week 2), đến các kiến trúc phức tạp như LangGraph (Week 4), bài học hôm nay mở ra một chương hoàn toàn mới về khả năng kết nối (Connectivity).
Dưới đây là tổng hợp chi tiết nội dung bài học "Day 1 - Intro to MCP: The USB-C of Agentic AI".
________________________________________
1. Tóm tắt cốt lõi (Core Summary)
•	Định nghĩa MCP: MCP (Model Context Protocol) là một tiêu chuẩn mở (open standard) do Anthropic khởi xướng, dùng để kết nối các mô hình AI với dữ liệu và công cụ bên ngoài.
•	Ẩn dụ "USB-C": Nếu trước đây mỗi thiết bị cần một loại dây cáp riêng, thì USB-C là chuẩn chung cho tất cả. Tương tự, MCP là chuẩn chung giúp mọi AI Agent kết nối với mọi nguồn dữ liệu/công cụ mà không cần viết code tích hợp riêng biệt ("glue code") cho từng cái.
•	Giá trị lớn nhất: Không nằm ở bản thân giao thức, mà nằm ở Hệ sinh thái (Ecosystem). Bạn viết tool một lần, cả thế giới Agent đều dùng được.
________________________________________
2. Nội dung chính
Nội dung buổi học mang tính định hướng chiến lược cho dự án Capstone sắp tới, tập trung vào các điểm sau:
A. Định vị MCP (What is it?)
•	Không phải là Framework: MCP không thay thế LangGraph, CrewAI hay OpenAI Agents SDK. Nó không dùng để điều phối luồng đi (Flow) hay quản lý trạng thái (State).
•	Là một Giao thức (Protocol): Nó quy định cách "người mua" (AI Client) và "người bán" (Server chứa dữ liệu/tool) nói chuyện với nhau.
•	Mục tiêu: Giúp tích hợp các Agent của bạn với các công cụ (Tools), tài nguyên (Resources - RAG), và lời nhắc (Prompts) do người khác viết một cách dễ dàng.
B. Tại sao lại hào hứng với MCP?
1.	Khả năng chia sẻ (Shareability): Một lập trình viên viết công cụ truy cập Google Drive. Nhờ MCP, bạn có thể lấy công cụ đó cắm ngay vào Agent của mình mà không cần quan tâm họ viết bằng Python hay TypeScript.
2.	Loại bỏ "Glue Code": Trước đây (như ở Week 1 & 2), để nối Agent với Database, bạn phải tự viết hàm, tự định nghĩa JSON Schema. Với MCP, việc kết nối trở nên "không ma sát" (frictionless).
3.	Hiệu ứng mạng lưới: Hàng nghìn công cụ MCP đang được cộng đồng xây dựng. Agent của bạn lập tức trở nên mạnh mẽ hơn nhờ tận dụng được kho vũ khí này.
C. Sự hiểu lầm thường gặp
•	Giảng viên nhấn mạnh: Nếu bạn tự viết tool cho riêng mình dùng (như cách dùng @function_tool trong OpenAI SDK ở Tuần 2), thì MCP làm mọi thứ phức tạp hơn.
•	MCP chỉ thực sự tỏa sáng khi bạn muốn kết nối với công cụ của người khác hoặc muốn công cụ của mình chạy được trên nhiều nền tảng khác nhau (Claude Desktop, Cursor, v.v.).
________________________________________
3. Kiến trúc & Quy trình (Architecture Concept)
Mặc dù bài học chưa đi sâu vào sơ đồ kỹ thuật chi tiết, nhưng mô hình tư duy (Mental Model) của MCP hoạt động như sau:
1.	MCP Host (Vật chủ): Nơi ứng dụng AI chạy (ví dụ: Claude Desktop App, hoặc IDE Cursor, hoặc ứng dụng Agent bạn viết).
2.	MCP Client: Phần mềm bên trong Host chịu trách nhiệm kết nối.
3.	MCP Server: Một chương trình chạy độc lập, cung cấp các Công cụ (Tools), Tài nguyên (Resources) hoặc Lời nhắc (Prompts).
o	Ví dụ: Một MCP Server cho GitHub, một MCP Server cho Google Calendar.
4.	Kết nối: Client kết nối với Server (thường qua stdio hoặc SSE), Server gửi danh sách Tools cho Client. Client (Agent) quyết định gọi Tool nào và gửi lệnh thực thi.

109. Day 1 - Understanding MCP Hosts, Clients, and Servers 
Chào bạn, tôi là trợ lý giảng viên AI Engineering của bạn.
Tiếp nối bài giới thiệu khái quát, bài học "Day 1 - Understanding MCP Hosts, Clients, and Servers" đi sâu vào "cơ sở hạ tầng" kỹ thuật của MCP. Đây là bài học cực kỳ quan trọng để bạn hiểu cách các mảnh ghép kết nối với nhau trước khi bắt tay vào code.
Dưới đây là tổng hợp chi tiết nội dung bài học:
1. Tóm tắt cốt lõi (Core Summary)
•	Bộ ba kiến trúc: MCP hoạt động dựa trên mối quan hệ giữa Host (Ứng dụng chính), Client (Cầu nối), và Server (Nhà cung cấp công cụ).
•	Sự nhầm lẫn về "Server": Dù gọi là "MCP Server", nhưng trong 90% trường hợp, nó là một tiến trình chạy cục bộ (locally) ngay trên máy tính của bạn, không phải một máy chủ từ xa trên đám mây.
•	Giao thức vận chuyển: Có hai cách để Client và Server nói chuyện với nhau: Stdio (phổ biến nhất, chạy cục bộ) và SSE (Server-Sent Events, dùng cho kết nối từ xa hoặc web).
________________________________________
2. Nội dung chính
A. Giải phẫu kiến trúc MCP (The Anatomy of MCP)
Bài học định nghĩa 3 thành phần không thể tách rời:
1.	MCP Host (Vật chủ):
o	Là ứng dụng tổng thể (Overall Application) nơi Agent "sống".
o	Ví dụ: Claude Desktop App, hoặc ứng dụng AI bạn tự viết bằng OpenAI Agents SDK (như chúng ta sẽ làm trong Lab).
o	Chức năng: Quản lý vòng đời của Agent, hiển thị giao diện chat, điều phối luồng.
2.	MCP Client (Khách):
o	Là một phần mềm nhỏ nằm bên trong Host.
o	Hoạt động như một "Plugin".
o	Nguyên tắc: Tỉ lệ 1:1 (Mỗi Client kết nối với một MCP Server cụ thể). Nếu bạn dùng 5 công cụ từ 5 nguồn khác nhau, Host sẽ khởi chạy 5 Clients.
3.	MCP Server (Máy chủ):
o	Chạy bên ngoài Host (nhưng thường vẫn trên cùng một máy tính).
o	Chức năng: Cung cấp Tools, Context (Dữ liệu), và Prompts cho Client.
o	Ví dụ thực tế: "Fetch MCP Server" là một server giúp Agent truy cập internet.
B. Cơ chế vận chuyển (Transport Mechanisms)
Làm sao Host/Client nói chuyện với Server?
1.	Stdio (Standard Input/Output):
o	(Trong transcript bị phiên âm sai thành "Studio").
o	Đây là cách phổ biến nhất. Host khởi chạy Server như một tiến trình con (subprocess).
o	Giao tiếp trực tiếp qua luồng dữ liệu vào/ra chuẩn của máy tính. Nhanh, đơn giản, bảo mật cục bộ.
o	Dùng cho: Các Server cài đặt cục bộ (Local Servers).
2.	SSE (Server-Sent Events):
o	(Trong transcript bị phiên âm sai thành "SW").
o	Sử dụng kết nối HTTPs, cho phép server "bắn" dữ liệu về client (streaming).
o	Dùng cho: Các Server chạy từ xa (Remote/Hosted Servers) - ví dụ bạn có một máy chủ doanh nghiệp chứa tool nội bộ và muốn Agent kết nối vào đó.

3. Kiến trúc & Quy trình (Architecture & Workflow)
Đây là phần quan trọng nhất để hình dung cách dữ liệu di chuyển.
Mô hình 1: Local MCP (Phổ biến nhất)
Đây là cấu hình bạn sẽ dùng trong hầu hết khóa học và thực tế.
•	Máy tính của bạn (The Box): Chứa tất cả mọi thứ.
o	Host: Đang chạy (ví dụ: file Python my_agent.py).
o	MCP Server (Process): Chạy ngầm. Ví dụ: filesystem-server để đọc file.
o	Kết nối: Host dùng Stdio để ra lệnh cho Server.
Mô hình 2: Remote MCP (Ít gặp hơn)
•	Máy tính của bạn: Chạy Host và Client.
•	Máy chủ từ xa (Cloud): Chạy MCP Server.
•	Kết nối: Dùng SSE qua internet.
Mô hình 3: Hybrid (Ví dụ "Fetch Server")
•	Server chạy cục bộ trên máy bạn (dùng Stdio).
•	Nhưng Server này lại gọi ra Internet để lấy dữ liệu.
•	Quy trình:
1.	Agent (trong Host) cần đọc một trang web -> Gửi lệnh cho Client.
2.	Client chuyển lệnh qua Stdio tới "Fetch Server".
3.	"Fetch Server" bật trình duyệt không đầu (Headless Browser) -> Tải trang web từ Internet.
4.	Trả kết quả text về cho Client -> Agent xử lý.

Bài học này là lý thuyết nền tảng (Lecture), chưa có file code thực hành đi kèm. Tuy nhiên, dựa trên mô tả về "Fetch MCP Server", ta có thể phân tích logic hoạt động của nó như sau (để chuẩn bị cho bài Lab):
Logic của Fetch MCP Server:
1.	Dependency: Sử dụng thư viện Playwright (của Microsoft) hoặc Selenium.
2.	Input: Nhận một URL từ Agent.
3.	Action:
o	Khởi tạo một "Headless Browser" (Trình duyệt Chrome/Firefox chạy ngầm không có giao diện).
o	Điều hướng đến URL.
o	Đợi trang tải xong (render JavaScript nếu cần).
o	Trích xuất nội dung văn bản (document.body.innerText).
4.	Output: Trả về văn bản thô (markdown/text) cho Agent đọc.
Lưu ý: Logic này được đóng gói trong Server. Agent của bạn không cần cài Playwright, chỉ cần kết nối với Server này là có khả năng duyệt web.

Dưới đây là tổng hợp chi tiết bài học "Day 1 - Using MCP Servers with OpenAI Agents SDK".

1. Tóm tắt cốt lõi (Core Summary)

•	Ví dụ thực tế: Sử dụng "Fetch MCP Server" (một server giúp duyệt web) để minh họa cách cấu hình và sức mạnh của việc mô tả tool (Tool Description).

3. Phân tích Code (Code Analysis)
Dựa trên nội dung bài giảng và logic trong 1_lab1.ipynb, dưới đây là phân tích các khối code quan trọng nhất.
Khối 1: Định nghĩa tham số cho MCP Server (The Parameters)
Logic ở đây là chúng ta không cài đặt server như một thư viện Python (pip install), mà chúng ta định nghĩa một lệnh CLI để chạy nó như một tiến trình độc lập.
Python
from mcp import StdioServerParameters

# Cấu hình để chạy "Fetch Server"
# Fetch Server là một công cụ giúp Agent duyệt web và lấy nội dung
fetch_mcp_server = StdioServerParameters(
    command="uvx", # Sử dụng 'uvx' (một công cụ của 'uv') để chạy gói Python mà không cần cài đặt vĩnh viễn
    args=["mcp-server-fetch"], # Tên của gói MCP Server cần chạy
    env=None # Có thể truyền biến môi trường nếu cần
)
•	Giải thích:
o	command="uvx": Đây là điểm thú vị. Thay vì cài đặt server vào máy, uvx sẽ tải phiên bản mới nhất về, chạy nó trong môi trường cách ly, và xóa đi khi xong (hoặc cache lại). Điều này đảm bảo bạn luôn dùng bản mới nhất.
o	args=["mcp-server-fetch"]: Tên của server chúng ta muốn gọi.
Khối 2: Kết nối và Lấy danh sách công cụ (Connect & List Tools)
Đây là nơi "ma thuật" xảy ra. SDK sẽ đóng vai trò là Client, kết nối với Server vừa định nghĩa ở trên.
Python
from openai_agents.mcp import McpServer

# Sử dụng context manager (async with) để quản lý vòng đời kết nối
# Khi thoát khỏi khối 'with', kết nối sẽ tự đóng và server con sẽ bị tắt (kill process)
async with McpServer(fetch_mcp_server) as server:
    
    # Yêu cầu Server liệt kê tất cả công cụ nó có
    # list_tools() gửi một request JSON-RPC đến server và đợi phản hồi
    tools = await server.get_tools()
    
    # In ra để kiểm tra xem chúng ta nhận được gì
    for tool in tools:
        print(f"Tool Name: {tool.name}")
        print(f"Description: {tool.description}")
•	Giải thích logic:
o	McpServer(fetch_mcp_server): SDK sẽ ngầm khởi chạy một subprocess (tiến trình con) bằng lệnh uvx mcp-server-fetch.
o	Giao tiếp diễn ra qua Stdio (Standard Input/Output) của tiến trình con đó.
o	get_tools(): Client hỏi "Bạn làm được gì?", Server trả lời "Tôi có tool tên là fetch, dùng để đọc web...".

4. Kiến thức liên quan & Mở rộng (Insights)
1. Sức mạnh của "Tool Description" (Prompt Engineering trong Code)
Trong bài, giảng viên chỉ ra một chi tiết đắt giá trong mô tả của công cụ fetch:
"Although originally you did not have internet access and were advised to refuse..., this tool now grants you internet access."
(Mặc dù ban đầu bạn không có quyền truy cập internet..., công cụ này giờ đây cấp quyền đó cho bạn.)
•	Tại sao cần câu này?
o	Các mô hình LLM (như GPT-4, Claude) thường được huấn luyện an toàn (Safety Training) để từ chối các yêu cầu truy cập internet ("I cannot browse the web").
o	Mô tả của MCP Tool hoạt động như một System Prompt injection. Nó "ghi đè" niềm tin của mô hình, cho phép mô hình tự tin sử dụng công cụ.
o	Bài học: Khi viết tool cho Agent, phần mô tả (description) quan trọng không kém phần code logic.
2. Tại sao dùng uvx (hoặc npx)?
•	Trong hệ sinh thái MCP, các Server thường được viết bằng Python hoặc TypeScript.
•	uvx (của Python uv) và npx (của Node.js) cho phép chạy các tool này ngay lập tức (ephemeral execution) mà không cần bạn phải pip install thủ công, lo lắng về xung đột dependency hay quản lý phiên bản. Đây là tiêu chuẩn hiện đại để phân phối MCP Server.
3. Khắc phục sự cố Windows (WSL)
•	Nếu bạn dùng Windows, hãy đảm bảo mở VS Code (hoặc Cursor) và cài đặt Extension "WSL". Sau đó bấm vào góc dưới bên trái (biểu tượng >< màu xanh) -> chọn "New Window using Distro..." -> chọn Ubuntu. Lúc này, terminal của bạn sẽ là Linux thực thụ.

from mcp import StdioServerParameters

# Cấu hình để chạy Playwright Server bằng Node.js
playwright_server = StdioServerParameters(
    command="npx",  # Dùng npx của Node thay vì uvx của Python

    env=None
)
•	Giải thích:
o	command="npx": Lệnh để chạy một gói npm mà không cần cài đặt toàn cục (tương tự uvx).
o	args: Tên gói chính thức từ Anthropic (@modelcontextprotocol/server-playwright).
o	Khi chạy, server này sẽ trả về hàng tá tools (click, screenshot...) thay vì chỉ 1 tool như fetch.
Khối 2: Cấu hình FileSystem Server (Có tham số dòng lệnh)
Python
import os

# Xác định đường dẫn thư mục an toàn
sandbox_path = os.path.abspath("./sandbox")

filesystem_server = StdioServerParameters(
    command="npx",
    args=[
        "-y",
        "@modelcontextprotocol/server-filesystem", # Tên gói npm
        sandbox_path # QUAN TRỌNG: Truyền đường dẫn được phép truy cập
    ],
    env=None
)
•	Giải thích:
o	Tham số sandbox_path được truyền vào args. Đây là cách chúng ta cấu hình Server ngay khi khởi động.
o	Nếu Agent cố gắng đọc file nằm ngoài sandbox_path, Server sẽ từ chối và báo lỗi. Đây là cơ chế bảo mật cốt lõi của MCP.

3. Phân tích Code (Logic & Implementation)
Đoạn code dưới đây (từ file 1_lab1.ipynb) minh họa cách kết hợp 2 Server vào 1 Agent.
Python
# 1. Định nghĩa tham số cho 2 Server riêng biệt
# Server 1: Quản lý File
mcp_server_files = StdioServerParameters(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-filesystem", sandbox_path]
)

# Server 2: Trình duyệt Web
mcp_server_browser = StdioServerParameters(
    command="npx",
    args=["-y", "@modelcontextprotocol/server-playwright"]
)

# 2. Khởi tạo Agent với danh sách Server
# Chú ý tham số 'mcp_servers' nhận vào một list [...]
agent = Agent(
    name="Investigator",
    instructions="You browse the internet... Be persistent...",
    model="gpt-4o-mini",
    mcp_servers=[mcp_server_files, mcp_server_browser] # <-- Sức mạnh nằm ở đây
)

# 3. Chạy Agent
with trace("investigate"):
    result = await Runner.run(agent, "Find a great recipe for Banoffee Pie, then summarize it in markdown to banoffee.md")
Giải thích Logic:
•	mcp_servers=[...]: Đây là điểm cải tiến vượt bậc so với cách viết tool truyền thống. Bạn không cần viết code glue (keo dán) để nối tool vào Agent. SDK tự động:
1.	Khởi chạy cả 2 process con (File Server & Browser Server).
2.	Lấy danh sách tool từ cả 2 (ví dụ: write_file từ Server 1 và Maps, click từ Server 2).
3.	Gộp tất cả vào context của LLM.
•	Luồng suy luận của AI:
o	AI nhận lệnh -> Phân tích cần tìm tin -> Gọi Maps (Tool Browser).
o	AI đọc được nội dung -> Phân tích cần lưu file -> Gọi write_file (Tool File).
o	Tất cả diễn ra tự động.

3.	Học tập (Learning): Tự xây dựng giúp bạn hiểu sâu về cơ chế hoạt động bên trong (nuts and bolts) của giao thức.

Python
# accounts.py
# ... (imports)

# Class đại diện cho một tài khoản
class Account(BaseModel):
    name: str
    balance: float
    # ... (các trường dữ liệu khác)

    # Hàm mua cổ phiếu - Logic nghiệp vụ phức tạp
    def buy_shares(self, symbol: str, quantity: int, rationale: str) -> str:
        """ Buy shares of a stock if sufficient funds are available. """
        # 1. Lấy giá cổ phiếu hiện tại
        price = get_share_price(symbol)
        # 2. Tính toán chi phí (bao gồm phí spread)
        buy_price = price * (1 + SPREAD)
        total_cost = buy_price * quantity
        
        # 3. Kiểm tra số dư (Validation)
        if total_cost > self.balance:
            raise ValueError("Insufficient funds to buy shares.")
        
        # 4. Cập nhật danh mục đầu tư và trừ tiền
        self.holdings[symbol] = self.holdings.get(symbol, 0) + quantity
        # ... (lưu transaction và update balance)
        return "Completed. Latest details:\n" + self.report()
•	Logic: Xử lý tính toán tiền, kiểm tra điều kiện (đủ tiền không), cập nhật cơ sở dữ liệu.
•	Mục đích: Cung cấp nền tảng chức năng để MCP Server gọi đến.
File 2: accounts_server.py (MCP Server - Quan trọng nhất)
Đây là lớp vỏ bọc (Wrapper) biến code Python thường thành MCP.
Python
# accounts_server.py
from mcp.server.fastmcp import FastMCP
from accounts import Account # Import logic nghiệp vụ gốc

# Khởi tạo một MCP Server với tên là "accounts_server"
mcp = FastMCP("accounts_server")

# @mcp.tool() là decorator biến hàm Python thành công cụ cho AI
# AI sẽ đọc Docstring bên dưới để hiểu cách dùng tool này
@mcp.tool()
async def buy_shares(name: str, symbol: str, quantity: int, rationale: str) -> float:
    """Buy shares of a stock. 
    
    Args:
        name: The name of the account holder
        symbol: The symbol of the stock
        quantity: The quantity of shares to buy
        rationale: The rationale for the purchase
    """
    # Gọi logic nghiệp vụ gốc từ accounts.py
    # MCP Server chỉ làm nhiệm vụ chuyển tiếp (delegation)
    return Account.get(name).buy_shares(symbol, quantity, rationale)

# Định nghĩa một Resource (Tài nguyên đọc thụ động)
# Cấu trúc URI giống URL: accounts://...
@mcp.resource("accounts://accounts_server/{name}")
async def read_account_resource(name: str) -> str:
    account = Account.get(name.lower())
    return account.report()

# Điểm khởi chạy server
if __name__ == "__main__":
    # Chạy server qua giao thức stdio (input/output chuẩn)
    mcp.run(transport='stdio')
•	Logic:
o	Sử dụng @mcp.tool() để đăng ký hàm với server.
o	Docstring là cực kỳ quan trọng: Nó chính là "Prompt" hướng dẫn cho LLM biết khi nào nên dùng hàm này và tham số cần điền là gì.
o	Server không chứa logic tính toán, nó chỉ gọi sang Account.get(name)....

# Cell cấu hình để chạy MCP Server
# Chúng ta không import server như thư viện, mà chạy nó như một chương trình riêng (subprocess)

# Khởi tạo kết nối Client với Server
async with MCPServerStdio(params=params, client_session_timeout_seconds=30) as mcp_server:
    # Tạo Agent và cung cấp mcp_server vào danh sách server
    agent = Agent(
        name="account_manager", 
        instructions=instructions, 
        model=model,

4. Kiến thức liên quan & Mở rộng
1. FastMCP là gì?
Trong code accounts_server.py, bạn thấy sử dụng FastMCP. Đây là một lớp tiện ích (utility class) cấp cao của Anthropic SDK.
•	Trước đây (Low-level): Bạn phải tự định nghĩa JSON Schema, tự xử lý vòng lặp request/response.
•	FastMCP (High-level): Tự động sinh JSON Schema từ Type Hint của Python (ví dụ name: str -> {"type": "string"}) và Docstring. Nó giúp việc viết MCP Server dễ như viết hàm Python thường.
2. Tools vs. Resources
Bài học giới thiệu hai khái niệm trong MCP:
•	Tools (@mcp.tool): Hành động chủ động, có thể thay đổi dữ liệu (Side effects), cần tham số đầu vào. Ví dụ: buy_shares (làm thay đổi số dư), send_email.
•	Resources (@mcp.resource): Dữ liệu thụ động, chỉ đọc (Read-only), giống như đọc một file hay một trang web. Ví dụ: read_account_resource (xem báo cáo). Agent coi đây như là "bối cảnh" (context) có thể tham chiếu tới.
3. Tại sao lại dùng Subprocess (uv run ...)?
Tại sao không import accounts_server trực tiếp vào Notebook?
•	Cách ly (Isolation): MCP Server được thiết kế để chạy độc lập. Nếu Server bị lỗi (crash), nó không làm sập Agent chính.
•	Đa ngôn ngữ: Agent của bạn có thể viết bằng Python, nhưng MCP Server có thể là một file .js chạy bằng Node.js. Giao tiếp qua stdio cho phép điều này.
4. Quy trình phát triển (Mental Model)
Khi bạn muốn đưa một hệ thống cũ lên AI Agent:
1.	B1: Viết/Refactor code logic nghiệp vụ sao cho sạch sẽ (như accounts.py).
2.	B2: Viết một lớp "Adapter" (MCP Server) để bọc các hàm cần thiết.
3.	B3: Viết Docstring thật kỹ cho lớp Adapter này (đây chính là viết Prompt cho AI).
4.	B4: Cấu hình Agent để kết nối tới file Adapter đó.

File: accounts_client.py (Cách viết Client thủ công)
Đây là file thể hiện cách hoạt động "bên dưới nắp capo". Nó đặc biệt hữu ích khi bạn muốn đọc Resources.
Python
import mcp
from mcp.client.stdio import stdio_client
from mcp import StdioServerParameters

# Cấu hình server
params = StdioServerParameters(command="uv", args=["run", "accounts_server.py"], env=None)

# Hàm thủ công để lấy danh sách tools (SDK đã làm hộ việc này, nhưng đây là code gốc)
async def list_accounts_tools():
    # Mở kết nối Stdio
    async with stdio_client(params) as streams:
        # Tạo phiên làm việc (Session)
        async with mcp.ClientSession(*streams) as session:
            await session.initialize() # Bắt buộc: Khởi tạo giao thức
            tools_result = await session.list_tools() # Gửi lệnh JSON-RPC hỏi tool
            return tools_result.tools

# Hàm đọc RESOURCES (Quan trọng: SDK Agent thường không tự làm việc này)
# Mục đích: Đọc dữ liệu tĩnh từ server thông qua URI
async def read_accounts_resource(name):
    async with stdio_client(params) as streams:
        async with mcp.ClientSession(*streams) as session:
            await session.initialize()
            
            # Đọc resource theo định dạng URI: protocol://server/resource_id
            # Ở đây là: accounts://accounts_server/{name}
            result = await session.read_resource(f"accounts://accounts_server/{name}")
            
            # Trả về nội dung text của resource
            return result.contents[0].text
Giải thích logic read_accounts_resource:
1.	Khác với Tool (là hàm), Resource giống như một file ảo.
2.	Client kết nối và gửi yêu cầu "đọc" tới đường dẫn accounts://....
3.	Server (trong file accounts_server.py) sẽ chặn yêu cầu này tại decorator @mcp.resource, chạy hàm tương ứng (account.report()) và trả về chuỗi văn bản.

4. Kiến thức liên quan & Mở rộng
1. Tools vs. Resources (Sự khác biệt quan trọng)
•	Tools: Dùng cho hành động (Actions). Có thể thay đổi trạng thái (mua/bán), cần tham số đầu vào, Agent chủ động quyết định gọi.
•	Resources: Dùng cho bối cảnh (Context). Là dữ liệu thụ động (read-only), Agent thường đọc nó để lấy thông tin nền (như file log, cấu hình, báo cáo lịch sử) trước khi ra quyết định.
2. Tại sao "Date Server" là một ví dụ tồi trong thực tế nhưng tốt cho học tập?
•	Thực tế: LLM cần biết ngày giờ để trả lời đúng (ví dụ: "Hôm qua là thứ mấy?"). Tuy nhiên, gọi một tool get_date() tốn 1 vòng lặp (round-trip) request mạng/process -> Chậm & tốn token. Cách tốt nhất là chèn ngày hiện tại trực tiếp vào System Prompt.
•	Học tập: Nó đủ đơn giản để bạn tập trung vào việc thiết lập Server/Client mà không bị rối bởi logic nghiệp vụ phức tạp.
3. Cấu trúc URI của Resource
Trong code, bạn thấy accounts://accounts_server/{name}.
•	Đây là chuẩn định danh tài nguyên của MCP.
•	Nó giúp phân biệt tài nguyên của Server này với Server khác khi một Agent kết nối với nhiều Server cùng lúc.
Bước tiếp theo: Bạn có thể thử làm bài tập "Calculator" (Máy tính) như giảng viên gợi ý: Tạo một server có tool add(a, b), multiply(a, b) và kết nối Agent vào để thực hiện phép tính.

o	Server chạy trên máy chủ của bên thứ ba.

•	Vấn đề: Các phương pháp nhớ vector (RAG) thường tốt trong việc tìm kiếm sự tương đồng (similarity) nhưng kém trong việc hiểu cấu trúc mối quan hệ (structure/relationship).

o	Node: Ed, AI Course, MCP.
o	Edge: Ed --(dạy)--> AI Course. AI Course --(chứa)--> MCP.

•	Bạn sẽ thấy hai lệnh này lặp lại liên tục.
•	npx: Dùng để chạy các MCP Server viết bằng JavaScript/TypeScript (Hệ sinh thái Node).
•	uvx (hoặc uv run): Dùng để chạy các MCP Server viết bằng Python.
•	MCP là giao thức "đa ngôn ngữ" (Polyglot), Host (Agent) có thể viết bằng Python nhưng vẫn dùng tốt Server viết bằng JS.
3. Tại sao lại dùng Local Database (ed.db)?
•	Trong ví dụ Memory, việc dùng file SQLite cục bộ (./memory/ed.db) minh họa tính chất Stateful (có trạng thái) của MCP Server.
•	Server không chỉ xử lý logic mà còn có thể quản lý dữ liệu riêng của nó, độc lập với Agent. Nếu bạn tắt Agent và bật lại, dữ liệu trong ed.db vẫn còn đó.

3.	Triển khai: Cloudflare cung cấp công cụ để tự tạo và deploy Remote MCP Server, hỗ trợ xác thực (Authentication), nhưng đây chưa phải là thực hành phổ biến trong cộng đồng vào thời điểm hiện tại.

4. Kiến thức liên quan & Mở rộng
1. Rate Limiting (Giới hạn tốc độ)
•	Là cơ chế của nhà cung cấp API để ngăn chặn việc lạm dụng hoặc quá tải hệ thống.
•	Khi làm việc với API bên thứ 3 (đặc biệt là Free Tier), lập trình viên AI Engineer phải luôn tính đến chiến lược Caching (lưu đệm) hoặc Backoff (thử lại sau một khoảng thời gian) để tránh lỗi 429 Too Many Requests.
2. Dữ liệu EOD (End-Of-Day) vs Realtime
•	EOD: Giá chốt phiên của ngày hôm qua. Thích hợp cho phân tích xu hướng dài hạn, học tập.
•	Realtime/Delayed: Giá hiện tại (hoặc trễ 15p). Thích hợp cho trading bot thực tế.
•	MCP Server của chúng ta được thiết kế linh hoạt để hỗ trợ cả hai tùy vào biến môi trường POLYGON_PLAN.
3. Tại sao không dùng server có sẵn của Polygon?
•	Trong Notebook, giảng viên có đề cập đến phần "Polygon.io Part 2". Polygon thực sự có cung cấp một MCP Server chính chủ (@polygon.io/mcp-server).
•	Tuy nhiên, server chính chủ này thường thiết kế cho người dùng trả phí với đầy đủ tính năng. Để học tập và dùng gói miễn phí hiệu quả nhất, việc tự viết server (market_server.py) với logic caching tùy chỉnh là bài tập tốt hơn và thực tế hơn cho kỹ sư.

3. Kiến trúc & Quy trình (Architecture & Pipeline)
Hệ thống trong bài học này được tổ chức theo mô hình phân cấp (Hierarchical):
Sơ đồ tư duy:
Plaintext
[Human User]
    |
    v
[Trader Agent "Ed"]
    | -- Kết nối trực tiếp --> [Accounts MCP Server] (Quản lý tiền/cổ phiếu)
    | -- Kết nối trực tiếp --> [Market MCP Server] (Lấy giá thị trường)
    | -- Kết nối trực tiếp --> [Push MCP Server] (Gửi thông báo)
    |
    | -- Sử dụng Tool --> [Researcher Tool]
                                |
                                v
                          [Researcher Agent]
                                | -- Kết nối --> [Brave Search MCP] (Tìm tin)
                                | -- Kết nối --> [Fetch MCP] (Đọc tin)
Quy trình hoạt động:
1.	Trader nhận nhiệm vụ quản lý danh mục đầu tư.
2.	Trader cần thông tin thị trường -> Gọi Researcher Tool.
3.	Researcher (bên trong tool) tự động dùng Brave/Fetch để tổng hợp tin tức -> Trả về kết quả cho Trader.
4.	Trader dùng Market MCP để check giá hiện tại.
5.	Trader ra quyết định -> Gọi Accounts MCP để Mua/Bán.
6.	Trader gọi Push MCP để thông báo "Tôi vừa mua AAPL".

4.3. Tạo Researcher Agent (Đại lý nghiên cứu)
Đây là kỹ thuật Hierarchical Agents (Đại lý phân cấp). Chúng ta tạo một Agent, sau đó đóng gói nó thành một Tool cho Agent khác dùng.
Python
# (Trích từ 4_lab4.ipynb)

# Hàm tạo Researcher Agent
async def get_researcher(mcp_servers) -> Agent:
    instructions = """You are a financial researcher...""" # Prompt hướng dẫn cách tìm tin
    researcher = Agent(
        name="Researcher",
        instructions=instructions,
        model="gpt-4.1-mini",
        mcp_servers=mcp_servers, # Trang bị Brave Search và Fetch
    )
    return researcher

# Hàm biến Researcher Agent thành một TOOL
async def get_researcher_tool(mcp_servers) -> Tool:
    researcher = await get_researcher(mcp_servers)
    # .as_tool() là phương thức đặc biệt của SDK (hoặc thư viện agents custom)
    # Nó biến Agent này thành một hàm mà Agent khác có thể gọi
    return researcher.as_tool(
            tool_name="Researcher",
            tool_description="This tool researches online for news and opportunities..."
        )
•	Điểm hay: Trader không cần biết cách dùng Google/Brave. Trader chỉ cần ra lệnh "Tìm tin về Amazon", và Researcher sẽ lo phần chi tiết kỹ thuật (search -> click -> read -> summarize).

4. Phân tích Code (push_server.py)
Đây là file code định nghĩa MCP Server dùng để gửi thông báo đẩy (Push Notification) qua dịch vụ bên thứ 3 là Pushover.
Python
import os
from dotenv import load_dotenv
import requests
from pydantic import BaseModel, Field
from mcp.server.fastmcp import FastMCP

# Tải biến môi trường (chứa User Key và API Token của Pushover)
load_dotenv(override=True)

pushover_user = os.getenv("PUSHOVER_USER")
pushover_token = os.getenv("PUSHOVER_TOKEN")
pushover_url = "https://api.pushover.net/1/messages.json"

# 1. Khởi tạo MCP Server bằng FastMCP
# Tên server là "push_server"
mcp = FastMCP("push_server")

# 2. Định nghĩa cấu trúc dữ liệu đầu vào cho Tool
# Giúp LLM hiểu chính xác cần truyền tham số gì
class PushModelArgs(BaseModel):
    message: str = Field(description="A brief message to push")

# 3. Định nghĩa Tool bằng decorator @mcp.tool()
@mcp.tool()
def push(args: PushModelArgs):
    """Send a push notification with this brief message"""
    
    # In ra console để debug (User Interface cục bộ)
    print(f"Push: {args.message}")
    
    # Chuẩn bị dữ liệu gửi đi
    payload = {"user": pushover_user, "token": pushover_token, "message": args.message}
    
    # Gửi request POST tới API của Pushover
    # Đây là hành động tương tác với thế giới bên ngoài (Side Effect)
    requests.post(pushover_url, data=payload)
    
    # Trả về kết quả cho Agent biết đã gửi thành công
    return "Push notification sent"

# 4. Chạy Server
if __name__ == "__main__":
    # Chạy qua giao thức stdio (Standard Input/Output)
    # Đây là cách Agent giao tiếp với Server này (qua đường ống pipe)
    mcp.run(transport="stdio")
Giải thích logic:
•	FastMCP: Thư viện giúp tạo MCP Server nhanh chóng mà không cần xử lý các giao thức JSON-RPC phức tạp bên dưới.
•	requests.post: Đây là đoạn code "kết nối thực tế". Agent ảo có thể tác động đến thế giới thực (điện thoại của bạn rung lên) thông qua dòng code này.
•	PushModelArgs: Việc sử dụng Pydantic giúp tạo ra JSON Schema chính xác để Agent (LLM) biết cách gọi hàm.

5. Kiến thức liên quan & Mở rộng
•	Pattern "Agent-as-a-Tool":
o	Đây là một mẫu thiết kế mạnh mẽ trong AI Engineering. Thay vì xây dựng một Agent khổng lồ biết làm tất cả mọi thứ (dễ bị ảo giác, sai sót), ta chia nhỏ thành các Agent chuyên biệt (Specialist).
o	Agent chính (Trader) chỉ cần biết: "Muốn có thông tin thì hỏi ông Researcher". Nó không cần biết Researcher dùng Google hay Bing, hay đọc báo nào. Điều này giúp giảm tải Context Window và tăng độ chính xác.
•	Trace Analysis (Phân tích dấu vết):
o	Trong bài, Trader mua rồi bán ngay lập tức. Nếu chỉ nhìn kết quả cuối cùng, ta sẽ thấy khó hiểu.
o	Nhờ Trace, ta biết lý do: Chiến lược là "Aggressive Day Trader" (Giao dịch trong ngày hung hãn) + Tin tức thị trường lúc đó -> Dẫn đến hành vi "lướt sóng" cực nhanh.

    def __init__(self, name: str, lastname="Trader", model_name="gpt-4o-mini"):
        self.name = name
        self.do_trade = True # Cờ để luân phiên hành động

    async def run_with_mcp_servers(self):
        # KỸ THUẬT QUAN TRỌNG: AsyncExitStack
        # Thay vì viết:
        # async with Server1:
        #    async with Server2:
        #       async with Server3:
        # ... (thụt đầu dòng quá sâu)
        
        async with AsyncExitStack() as stack:
            # 1. Kết nối tất cả Trader MCP Servers (Account, Market, Push)
            # stack.enter_async_context giúp "mở" kết nối và giữ nó sống trong khối lệnh này
            trader_mcp_servers = [
                await stack.enter_async_context(
                    MCPServerStdio(params, client_session_timeout_seconds=120)
                )
                for params in trader_mcp_server_params
            ]
            
            # 2. Kết nối tất cả Researcher MCP Servers (Brave, Fetch, Memory)
            # Lưu ý: cần truyền self.name để lấy đúng file Memory riêng của Trader đó
            async with AsyncExitStack() as stack:
                researcher_mcp_servers = [
                    await stack.enter_async_context(
                        MCPServerStdio(params, client_session_timeout_seconds=120)
                    )
                    for params in researcher_mcp_server_params(self.name)
                ]
                
                # Sau khi tất cả cửa đã mở, mới chạy Agent
                await self.run_agent(trader_mcp_servers, researcher_mcp_servers)

    async def run(self):
        try:
            await self.run_with_trace() # Chạy có giám sát (Tracing)
        except Exception as e:
            print(f"Error running trader {self.name}: {e}")
        
        # Đảo ngược trạng thái: Lần sau chạy sẽ làm việc khác (Trade <-> Rebalance)
        self.do_trade = not self.do_trade

1.	AsyncExitStack là gì?
o	Trong Python, with (Context Manager) dùng để quản lý tài nguyên (mở file, kết nối mạng) và đảm bảo chúng được đóng lại đúng cách.
o	Khi bạn cần mở số lượng tài nguyên không xác định trước (ví dụ: một list các server), bạn không thể viết code tĩnh.
o	AsyncExitStack cho phép bạn "nhét" bao nhiêu context manager vào ngăn xếp (stack) cũng được, và khi thoát khỏi khối lệnh, nó sẽ lần lượt đóng (exit) tất cả chúng theo thứ tự ngược lại. Đây là Best Practice cho các hệ thống dynamic.
2.	Quy trình Lab-to-Module:

o	Hãy bắt đầu ở Notebook -> Thử nghiệm Prompt -> Thử nghiệm Tool -> Khi ổn định mới Refactor thành Class/Module.
o	Lý do: Debug trong Notebook dễ hơn nhiều so với việc phải khởi động lại toàn bộ app khi sửa một lỗi nhỏ trong file .py.

from agents import TracingProcessor

# Kế thừa class TracingProcessor của SDK để tự xử lý log
class LogTracer(TracingProcessor):

    # Hàm này chạy khi Agent BẮT ĐẦU một chuỗi suy nghĩ (Trace)
    def on_trace_start(self, trace) -> None:
        name = self.get_name(trace)
        if name:
            # Ghi vào database: "Warren bắt đầu suy nghĩ..."
            write_log(name, "trace", f"Started: {trace.name}")

    # Hàm này chạy khi Agent gọi một TOOL hoặc thực hiện một bước nhỏ (Span)
    def on_span_start(self, span) -> None:
        name = self.get_name(span)
        # Lấy loại hành động (ví dụ: 'function', 'generation')
        type = span.span_data.type if span.span_data else "span"
        if name:
            message = "Started"
            # ... (Logic tạo thông báo chi tiết) ...
            # Ghi log chi tiết: "Warren đang gọi tool buy_shares..."
            write_log(name, type, message)
•	Ghi chú: Nhờ class này, mỗi bước đi của Agent đều được lưu vào bảng logs trong SQLite, giúp UI có thể hiển thị dòng chữ "Checking market data..." hay "Buying AAPL..." theo thời gian thực.

Python
# (Trích từ trading_floor.py)

async def run_every_n_minutes():
    # 1. Đăng ký Tracer tùy chỉnh
    # Để bắt các sự kiện suy nghĩ của Agent và ghi vào DB cho UI hiển thị
    add_trace_processor(LogTracer()) 
    
    # 2. Tạo danh sách 4 Trader (Warren, George, Ray, Cathie)
    traders = create_traders()
    
    # 3. Vòng lặp vô tận (Infinite Loop)
    while True:
        # Kiểm tra điều kiện thị trường hoặc cờ ép chạy
        if RUN_EVEN_WHEN_MARKET_IS_CLOSED or is_market_open():
            
            # KỸ THUẬT QUAN TRỌNG: Asyncio Gather
            # Chạy hàm .run() của tất cả trader CÙNG MỘT LÚC
            # Dấu * dùng để unpack list traders thành các tham số rời
            await asyncio.gather(*[trader.run() for trader in traders])
            
        else:
            print("Market is closed, skipping run")
        
        # 4. Ngủ N phút trước phiên tiếp theo
        await asyncio.sleep(RUN_EVERY_N_MINUTES * 60)

if __name__ == "__main__":
    # Điểm bắt đầu chương trình
    print(f"Starting scheduler to run every {RUN_EVERY_N_MINUTES} minutes")
    asyncio.run(run_every_n_minutes())
Giải thích logic:
•	LogTracer(): Được thêm vào đầu pipeline để "nghe lén" mọi hoạt động. Nếu không có dòng này, UI sẽ trống trơn dù Agent vẫn chạy ngầm.
•	asyncio.gather(...): Đây là kỹ thuật lập trình bất đồng bộ (Asynchronous Programming). Dù Python là đơn luồng (single-threaded), nhưng nhờ cơ chế await (chờ I/O như mạng, disk), nó có thể chuyển đổi qua lại giữa các Trader cực nhanh, tạo cảm giác chúng đang chạy song song.

•	Kỹ năng chuyển đổi: Các khái niệm cốt lõi (Tools, Structured Outputs, System Prompts) là giống nhau ở mọi framework. Nếu bạn giỏi một cái, bạn có thể dễ dàng học cái khác.
•	Lời khuyên vàng (Phần 1): Luôn bắt đầu từ Vấn đề (Problem) chứ không phải giải pháp (Solution), và phải có Thước đo (Metric) rõ ràng ngay từ đầu.
________________________________________
2. Nội dung chính
A. Đánh giá các Framework phổ biến (The Landscape)
Giảng viên đưa ra cái nhìn tổng quan và công tâm về các công cụ hiện nay:
1.	OpenAI Agents SDK:
o	Đặc điểm: Nhẹ (Lightweight), linh hoạt, không can thiệp sâu (stays out of the way).
o	Phù hợp với: Những người thích kiểm soát dòng code, thích sự đơn giản và muốn hiểu sâu về cơ chế hoạt động (như phong cách của khóa học này).
2.	CrewAI:
o	Đặc điểm: "Batteries included" (Trang bị tận răng). Cung cấp sẵn mọi thứ trong hộp.
o	Phù hợp với: Người thích cấu hình qua file YAML, muốn có kết quả nhanh mà không cần code quá nhiều phần nền tảng (plumbing), thích các công cụ trực quan hóa (low-code tools).
3.	LangGraph (LangChain ecosystem):
o	Đặc điểm: Chặt chẽ, khả năng tái lập cao (reproducible), tích hợp sâu với LangSmith để giám sát.
o	Phù hợp với: Các hệ thống doanh nghiệp cần quy trình luồng (workflow) rõ ràng và khả năng debug mạnh mẽ.
4.	Google Agent Development Kit (ADK):
o	Đặc điểm: Mới nổi, đang được Google đẩy mạnh (Version 1.0 production-ready).
o	Điểm độc đáo: Giới thiệu giao thức A2A (Agent to Agent) - cho phép các Agent tự khám phá và giao tiếp với nhau (tương tự ý tưởng của AutoGen Core nhưng ở quy mô giao thức).
5.	Hugging Face (smolagents) & Pydantic AI:
o	Các lựa chọn khác cũng rất thú vị, đơn giản và hiệu quả. Pydantic AI thậm chí còn là nguồn cảm hứng cho OpenAI Agents SDK.
B. 10 Lời khuyên cho dự án thực tế (Bắt đầu với 2 điều đầu tiên)
Giảng viên bắt đầu chia sẻ 10 lời khuyên xương máu cho một kỹ sư AI (Data Scientist), và đây là 2 điều đầu tiên quan trọng nhất:
Lời khuyên #1: Đừng bắt đầu với "Tôi muốn dùng AI Agent"
•	Sai lầm phổ biến: Rất nhiều người nhảy vào và nói "Tôi cần một con Agent để làm X". Đây là tư duy ngược (Solution-first).
•	Tư duy đúng: Hãy tập trung vào Vấn đề.
o	Vấn đề bạn đang giải quyết là gì?
o	Tại sao nó khó?
o	Sau khi hiểu rõ vấn đề, hãy tự hỏi: "AI Agent có phải là cách tốt nhất để giải quyết nó không?".
•	Đừng để sự cường điệu (Hype) dẫn dắt bạn.
Lời khuyên #2: Xác định Thước đo (Metric) và Dữ liệu
•	Sao Bắc Đẩu (North Star): Bạn cần một con số cụ thể để biết mình đã giải quyết thành công vấn đề hay chưa.
•	Quản lý dữ liệu (Curate Data): Để đo lường được Metric đó, bạn cần dữ liệu gì? Bạn đã có chưa?
•	Đây là tư duy chuẩn của một nhà Khoa học dữ liệu (Data Scientist): Nếu không đo lường được, bạn sẽ không thể cải thiện được (nhất là với sự ngẫu nhiên của LLM).
________________________________________
3. Kiến thức liên quan & Mở rộng
•	Google ADK vs. MCP:
o	MCP (Model Context Protocol): Giúp Agent kết nối với Công cụ/Dữ liệu (Agent <-> Tool).
o	Google A2A (Agent to Agent): Giúp Agent kết nối với Agent (Agent <-> Agent). Nó cho phép các Agent hỏi nhau: "Bạn làm được gì?" (Capability Discovery) thông qua "Agent Card".
•	Sự tương đồng giữa các Framework:
o	Dù bạn dùng LangGraph hay OpenAI SDK, bản chất bên dưới vẫn là gửi một danh sách tools (JSON schema) cho LLM, nhận về tool_calls, thực thi code Python, và gửi lại kết quả.
o	Vì vậy, đừng lo lắng nếu bạn chọn "sai" framework. Việc chuyển đổi (migrate) không quá khó khăn nếu bạn nắm vững tư duy cốt lõi.

129. Day 5 - 10 Essential Lessons for Building Agent Solutions
Chào bạn, tôi là trợ lý giảng viên AI Engineering của bạn.
Tiếp nối phần trước, chúng ta sẽ đi nốt phần còn lại của "10 bài học cốt lõi" dành cho một kỹ sư AI Agent. Dựa trên bản phiên âm bài giảng "129. Day 5 - 10 Essential Lessons for Building Agent Solutions", đây là những lời khuyên "xương máu" để giúp bạn xây dựng hệ thống thành công và tránh những cái bẫy phổ biến.
________________________________________
1. Tóm tắt cốt lõi (Core Summary)
•	Triết lý "Simple First": Luôn bắt đầu đơn giản hóa mọi thứ. Ưu tiên quy trình làm việc (Workflow) cứng trước khi trao quyền tự chủ (Autonomy).
•	Quy trình "Bottoms Up": Đừng vẽ kiến trúc lớn ngay từ đầu. Hãy xây dựng từng mảnh nhỏ (một Agent đơn lẻ) thật tốt rồi mới ghép lại.
•	Tư duy "Data Scientist": Đây là lời khuyên quan trọng nhất. Hãy cởi bỏ chiếc mũ "Kỹ sư phần mềm" (xây dựng theo thiết kế) và đội chiếc mũ "Nhà khoa học dữ liệu" (thử nghiệm, đo lường và khám phá).
•	Giải quyết vấn đề (Troubleshooting): Hầu hết vấn đề được giải quyết bằng Prompting tốt hơn và kiểm tra Trace, không phải bằng code phức tạp hay fine-tuning.

2. Nội dung chính: 8 Lời khuyên tiếp theo (Lesson 3 - 10)
Giảng viên tiếp tục danh sách từ lời khuyên số 3:
#3. Ưu tiên Workflow hơn Autonomy (Workflows > Autonomy)
•	Sai lầm: Vội vàng xây dựng hệ thống hoàn toàn tự chủ (Agent tự quyết định mọi thứ) ngay từ đầu.
•	Lời khuyên: Hãy bắt đầu bằng cách tiếp cận thứ ba (ngoài Tools và Handoffs): Sử dụng code Python thuần túy để điều phối từng bước (Orchestrator).
o	Bước 1: Gọi Agent A -> Nhận kết quả.
o	Bước 2: Dùng code Python xử lý.
o	Bước 3: Gọi Agent B.
•	Sau khi quy trình cứng này chạy ổn, mới dần dần chuyển sang cho Agent tự gọi Tool (tăng quyền tự chủ).
#4. Xây dựng từ dưới lên (Bottoms Up)
•	Dành cho Software Engineers: Đừng bắt đầu với một tờ giấy trắng và vẽ sơ đồ kiến trúc hệ thống Agent khổng lồ.
•	Cách làm đúng: Giải quyết một phần nhỏ của vấn đề bằng một Agent đơn giản. Khi nó hoạt động tốt, hãy thêm một Agent khác. Xây dựng nền tảng dựa trên những gì thực sự hoạt động, không phải trên lý thuyết.
#5. Bắt đầu đơn giản, mở rộng sau (Start Simple)
•	Nếu bạn viết hàng trăm dòng code ngay từ đầu và nó không chạy, bạn sẽ không biết lỗi ở đâu.
•	Bắt đầu với các khối xây dựng cơ bản. Chỉ tăng độ phức tạp khi phiên bản đơn giản đã hoạt động trơn tru.
#6. Dùng Model xịn nhất để Prototyping
•	Chiến lược: Bắt đầu với GPT-4o, Claude 3.5 Sonnet/Opus (các model thông minh nhất) trên tập dữ liệu nhỏ.
•	Mục đích: Để chứng minh ý tưởng (Proof of Concept) là khả thi về mặt lý thuyết.
•	Tối ưu sau: Khi đã chạy được, hãy thử chuyển xuống các model rẻ hơn/nhanh hơn (GPT-4o-mini, Flash) và tinh chỉnh Prompt để đạt hiệu suất tương đương.
#7. Đừng thần thánh hóa "Bộ nhớ" (Memory)
•	Bản chất: Đừng bị rối bởi các thuật ngữ "Short-term" hay "Long-term memory".
•	Thực tế: Tất cả chỉ là tìm cách nhét thông tin liên quan vào Prompt (Context Window).
•	Thay vì lo lắng về công nghệ vector database nào, hãy tập trung vào câu hỏi: "LLM cần thông tin gì để trả lời câu hỏi này? Và mình đã đưa thông tin đó vào Prompt chưa?".
#8. Prompting là chìa khóa sửa lỗi
•	Khi gặp khó khăn, đừng vội nghĩ đến Fine-tuning hay thay đổi mô hình RAG phức tạp.
•	Giải pháp: Hầu hết vấn đề được giải quyết bằng cách viết lại Prompt:
o	Đơn giản hóa chỉ thị.
o	Thêm ví dụ (Few-shot prompting).
o	Rõ ràng về định dạng đầu ra mong muốn.
#9. Luôn kiểm tra Dấu vết (Look at the Traces)
•	Ngay cả khi Agent trả lời đúng, hãy vẫn kiểm tra Trace.
•	Lý do: Có thể Agent đã gọi thừa tool, hoặc đi đường vòng, hoặc bị ảo giác nhẹ nhưng may mắn đúng. Việc kiểm tra giúp phát hiện các "gotcha" (lỗi tiềm ẩn) để tối ưu chi phí và tốc độ.
#10. Đội mũ "Nhà khoa học dữ liệu" (The Scientist Hat) - QUAN TRỌNG NHẤT
•	Kỹ sư AI cần 2 chiếc mũ: Kỹ sư phần mềm & Nhà khoa học dữ liệu.
•	Khi bắt đầu dự án: Hãy là Nhà khoa học.
•	Đừng hỏi: "Tôi nên dùng model nào? Prompt nào?".
•	Câu trả lời là: Thử nghiệm tất cả (Experiment). Không có đường tắt cho R&D (Nghiên cứu & Phát triển). Trực giác thường sai, chỉ có số liệu thực tế trên bài toán của bạn mới là câu trả lời đúng.

3. Phân tích Kỹ thuật & Code
Mặc dù bài này không cung cấp file code mới, nhưng giảng viên đề cập đến "Cách tiếp cận thứ ba" trong việc điều phối Agent. Chúng ta có thể hình dung logic code như sau:
Cách tiếp cận tự chủ (Autonomy - Khó kiểm soát lúc đầu):
Python
# Agent tự quyết định gọi Agent khác qua Tool
agent_A = Agent(tools=[agent_B_as_tool])
Runner.run(agent_A, "Làm nhiệm vụ X")
Cách tiếp cận "Workflow/Python Orchestration" (Khuyên dùng lúc đầu):
Python
# Kiểm soát luồng bằng Python (Deterministic)
result_1 = Runner.run(agent_A, "Làm bước 1")
processed_data = python_function(result_1) # Xử lý logic cứng
result_2 = Runner.run(agent_B, f"Làm bước 2 với dữ liệu {processed_data}")
-> Lợi ích: Bạn biết chính xác điều gì xảy ra ở từng bước. Dễ debug hơn nhiều so với việc để Agent tự "bơi".

4. Kiến thức liên quan & Mở rộng
•	R&D trong AI Engineering:
o	Khác với phần mềm truyền thống (nơi Input A luôn ra Output B), AI có tính xác suất (Probabilistic).
o	Do đó, quy trình làm việc phải là: Xây dựng -> Đo lường (Evaluation) -> Cải tiến. Bạn không thể "code một lần là xong".
•	Prompt Engineering vs. Fine-tuning:
o	Giảng viên nhấn mạnh Prompting. Theo nguyên tắc của OpenAI: "Đừng fine-tune cho đến khi bạn đã vắt kiệt sức mạnh của Prompt Engineering". Fine-tuning tốn kém, khó bảo trì và dễ làm mất khả năng tổng quát của model.
•	Traces (Quan sát):
o	Nhắc lại việc chúng ta đã dùng LogTracer trong bài trước. Đây là công cụ không thể thiếu để thực hiện lời khuyên #9.
